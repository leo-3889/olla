# v0.0.29 Release Prep - CB-Open Failover Fix + Bun Version Drift

## Purpose & scope

Two small, independent fixes required before cutting v0.0.29. This is a stabilisation
release: if it holds for a month it gets promoted to v0.1.0. Deliberately minimal -
no new circuit-breaker (CB) trip conditions, no behaviour changes beyond the two fixes
stated below.

1. **Live bug**: a request that lands on an Olla-engine endpoint whose per-endpoint
   circuit breaker is open fails the whole client request instead of failing over to
   another healthy endpoint.
2. **Build drift**: the local `make ready` Bun version floor doesn't match CI's.

Out of scope is listed explicitly in its own section below - read it before proposing
any change beyond what FR-1 through FR-6 state.

## Background (verified against `feature/campaign-fixes` @ 3785dec)

- `internal/adapter/proxy/olla/service_retry.go:76-80` - when `cb.IsOpen(...)` returns
  true, `proxyToSingleEndpoint` calls `s.RecordFailure(...)` for stats, then returns a
  plain `fmt.Errorf("circuit breaker open for endpoint %s", endpoint.Name)`.
- `internal/adapter/proxy/core/retry.go:185-188` - `ExecuteWithRetry`'s loop calls
  `IsConnectionError(lastErr)`; if false, it returns `lastErr` immediately as a hard
  failure. The plain `fmt.Errorf` above matches none of `IsConnectionError`'s branches
  (`net.Error`, `syscall.Errno` allowlist, or the `connectionErrors` string fallback at
  retry.go:354-362), so the client gets a hard failure while other endpoints in
  `availableEndpoints` are never tried.
- `internal/adapter/proxy/core/retry.go:194-199` - the non-idempotent "response already
  started" retry guard, which must continue to hold unchanged.
- `internal/adapter/proxy/core/retry.go:273-294` (`handleConnectionFailure`) - the path
  taken for genuine connection errors. It calls `markEndpointUnhealthy`, which
  1-strike-demotes the endpoint to `domain.StatusOffline` via
  `discoveryService.UpdateEndpointStatus`. This is a **global, persisted** endpoint
  health change and must **not** be triggered by a CB-open rejection.
- `internal/adapter/proxy/core/retry.go:308-314` (`buildFinalError`) - when
  `availableEndpoints` is empty it returns
  `fmt.Errorf("all endpoints failed with connection errors: %w", lastErr)`; otherwise
  `fmt.Errorf("max attempts (%d) reached: %w", maxRetries, lastErr)`. This error
  eventually reaches `Application.handleProxyError`
  (`internal/app/handlers/handler_proxy.go:573-594`), which - for any error that isn't
  an `http.MaxBytesError` - writes `http.StatusBadGateway` (502) with body
  `"Proxy error: %v"`. That 502 mapping is the existing behaviour for connection-error
  exhaustion; a CB-open exhaustion should read the same way to the client (a service
  reachability problem), not as a different/misleading class of error.
- **Sherpa has no circuit breaker at all** - confirmed by grep across
  `internal/adapter/proxy/sherpa/`; the only match is a comment
  (`sherpa/service.go:28`) explicitly deferring "circuit breaking, rate limiting, etc."
  to Olla. Sherpa's `proxyToSingleEndpoint` therefore never produces this error, so any
  change scoped to `IsConnectionError`/`ExecuteWithRetry` behaviour for this specific
  error is a guaranteed no-op for Sherpa - no Sherpa code path exercises it.
- Existing tests to model new tests on: `internal/adapter/proxy/core/retry_test.go`,
  `internal/adapter/proxy/core/retry_safety_test.go`.
- `resilience.Breaker.IsOpen(HalfOpenStaleness)` (called at `service_retry.go:74`)
  returns `(open bool, attempt int64)` - internals are out of scope, see below.

## Functional requirements

**FR-1 - Typed CB-open sentinel error.**
Add a typed sentinel error to `internal/adapter/proxy/core` (e.g.
`ErrCircuitBreakerOpen`, exact name at implementer's discretion, but it must be
exported and usable with `errors.Is`/`errors.As`). `olla/service_retry.go`'s CB-open
branch (currently `service_retry.go:76-80`) must construct its error by wrapping this
sentinel with the endpoint name (e.g. `fmt.Errorf("%w: endpoint %s", core.ErrCircuitBreakerOpen, endpoint.Name)`)
instead of the current plain `fmt.Errorf`. The existing `s.RecordFailure(...)` call on
this path is unchanged - stats semantics for CB-open rejections are out of scope.

**FR-2 - Failover on CB-open, without health demotion.**
`ExecuteWithRetry` (`internal/adapter/proxy/core/retry.go`) must treat a CB-open error
as failover-eligible: on `errors.Is(lastErr, core.ErrCircuitBreakerOpen)`, remove that
endpoint from `availableEndpoints` for this request and continue the loop - subject to
the same guards as today (context cancellation at retry.go:167-169, the non-idempotent
"response started" guard at retry.go:194-199, and `maxRetries`). This must happen
**without** calling `markEndpointUnhealthy` or otherwise mutating the endpoint's
persisted health/status - a CB-open attempt must never change endpoint health state.
This check must be evaluated before or alongside the existing
`if !IsConnectionError(lastErr)` gate at retry.go:185-188 so a CB-open error no longer
falls into that immediate-hard-failure branch.

**FR-3 - `IsConnectionError` semantics unchanged.**
`IsConnectionError` must continue to return `false` for `ErrCircuitBreakerOpen` (or
whatever error it's wrapped in) - do not add "circuit breaker open" to the
`connectionErrors` string list (retry.go:354-362) or otherwise make
`IsConnectionError` return true for it. `IsConnectionError`'s behaviour for every
other existing input (net.Error, syscall.Errno, the string fallback list,
`context.DeadlineExceeded`/`context.Canceled`) must be provably unchanged - this is
the design guardrail that keeps CB-open handling from ever reaching
`handleConnectionFailure`/`markEndpointUnhealthy`.

**FR-4 - Sensible client-facing error on total exhaustion.**
When every candidate endpoint is CB-open (`availableEndpoints` empties out via the
FR-2 path), `buildFinalError` must still produce a clear, service-unavailable-flavoured
error - this path is newly reachable and was previously unreachable for this error
class. Verify what HTTP status and body `handleProxyError` (handler_proxy.go:573-594)
actually maps the resulting error to today (currently 502 `"Proxy error: %v"` for any
non-`MaxBytesError`), and either confirm that mapping already reads sensibly for a
CB-open exhaustion, or adjust `buildFinalError`'s wrapped message text so the 502 body
doesn't misleadingly claim "connection errors" when the true cause was breaker state.
Do not change the HTTP status code mapping in `handleProxyError` - that is shared
machinery for all proxy errors and is out of scope for this changeset.

**FR-5 - Sherpa unaffected.**
Confirm (as part of implementation, with a note in the PR/commit) that Sherpa has no
circuit breaker and shares `core.ExecuteWithRetry`, so FR-1 through FR-4 are a no-op
for Sherpa's actual error set. No changes to any file under
`internal/adapter/proxy/sherpa/`.

**FR-6 - Bun version alignment.**
Update `makefile:12` from `BUN_VERSION := 1.1.0` to `BUN_VERSION := 1.3.5`, matching
`.github/workflows/ci.yml:29` and `.github/workflows/release.yml:10`. Verify no other
file in the repo references the old `1.1.0` pin before/after the change (a repo-wide
search for the literal `1.1.0` string, scoped to build/CI config, is sufficient
verification - no code searches this string for other purposes as far as is currently
known).

## Non-functional requirements

**NFR-1 - No new CB trip conditions.** Do not add any new condition that opens or
closes a circuit breaker. `resilience.Breaker` internals (ABA attempt tokens,
single-flight half-open admission, staleness windows) must not change.

**NFR-2 - Race-clean.** All new/changed tests must pass under `go test -race`.

**NFR-3 - Event-synchronised tests.** Per project convention, tests must synchronise
on events (channels, waitgroups, mock call counts), never on wall-clock `time.Sleep`.

**NFR-4 - `GOMAXPROCS=2` clean.** The full non-short suite must pass under
`GOMAXPROCS=2` (existing project convention for surfacing scheduling-order bugs).

**NFR-5 - No panics.** No new panics in production code; if a guard is needed, use the
project's existing CAS/`sync.Once` idioms - consistent with existing code in this
package.

## Data & interfaces

- New exported sentinel: `core.ErrCircuitBreakerOpen` (or implementer's chosen name),
  package `internal/adapter/proxy/core`. No other public API changes.
- No config schema changes, no new endpoints, no response header changes.
- `X-Olla-*` response headers are unaffected - a failed-over request still reports the
  endpoint that actually served it, per existing behaviour.

## Acceptance criteria

**AC-1 (FR-1, FR-2).** Circuit breaker open on endpoint A, endpoint B healthy, request
sent → response is 200, served by B (assert via `X-Olla-Endpoint` or equivalent). A's
endpoint health/status is asserted unchanged after the request (query the endpoint
repository/discovery service state, not just the absence of an error) - per house
testing rule, assert the state effect of the failure path, not only the returned
error.

**AC-2 (FR-2, FR-4).** Circuit breaker open on every candidate endpoint → the client
receives a clean, service-unavailable-flavoured error (assert the actual mapped HTTP
status and that the body text is coherent, not a raw Go error dump implying a
connection failure that didn't occur). No panic. No endpoint's health status changes
as a result of this request.

**AC-3 (existing guard, regression).** Non-idempotent request (e.g. POST), response
already started on the current attempt, next candidate endpoint is CB-open → no retry
is attempted; the partial response stands. This is the existing
`tracker.started && !isIdempotent(r.Method)` guard at retry.go:194-199 and must be
provably untouched by this change.

**AC-4 (FR-3, regression guard).** `IsConnectionError(wrapped ErrCircuitBreakerOpen)`
returns `false`. A table/regression test pins this so a future "helpful" fix doesn't
route CB-open through the connection-error/health-demotion path. Existing
`IsConnectionError` test cases (net.Error, syscall errnos, string fallbacks,
context.DeadlineExceeded/Canceled) remain green, unmodified in expected outcome.

**AC-5 (FR-5).** No diff under `internal/adapter/proxy/sherpa/`. A written note (PR
description or commit body) confirms sherpa's error set never reaches the new branch.

**AC-6 (FR-6).** `makefile:12` reads `BUN_VERSION := 1.3.5`. `make ready`'s bun
version-floor check now agrees with CI's. No other file still references the old
`1.1.0` pin.

**AC-7 (gate).** `make ci` exits 0. The full non-short test suite run explicitly under
`GOMAXPROCS=2` exits 0 (verify `go test`'s own process exit code, not just absence of
`FAIL` in the log). All comments touched or added are Australian English and explain
why, not what. No `Co-Authored-By` lines; commit messages are humanised one-liners.

## Assumptions

- The sentinel error's exact name/placement is left to the implementer (FR-1 says "at
  implementer's discretion") because the spec author has no strong reason to prefer
  one file/name over another and forcing one risks colliding with existing naming in
  `core`. Rejected alternative: mandate an exact symbol name - adds no value and
  slightly increases the risk of an awkward fit with existing error definitions in the
  package.
- FR-4 says "verify... and either confirm or adjust" rather than mandating a specific
  new status code, because the current 502-for-all-non-MaxBytesError mapping in
  `handleProxyError` is shared machinery serving many other error paths; changing that
  shared mapping is a bigger blast radius than this changeset should take on. Rejected
  alternative: mandate 503 Service Unavailable specifically - would require changing
  `handleProxyError`'s general dispatch logic, out of proportion for a "small,
  minimal" release-prep fix and not requested by the goal statement.
- WP-3 (Bun fix) is assumed trivial enough not to need a dedicated specialist agent;
  it can be picked up by whichever agent is already touching the repo, or done
  directly by the orchestrator.
